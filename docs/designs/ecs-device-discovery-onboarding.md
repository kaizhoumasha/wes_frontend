# Design: ECS 设备发现与显式接管

- Generated by `/office-hours` on 2026-09-01
- Reviewed with `/plan-eng-review` on 2026-09-01
- Branch: `codex/feature-ecs-device-discovery`
- Repo: `kaizhoumasha/wes_frontend`，配套后端 `wes_backend`
- Status: IMPLEMENTED — QA/SHIP IN PROGRESS
- Scope ceiling: frontend-only reuse of the existing MANUAL_DEBUG preflight

## Problem Statement

当前“设备管理”只提供 WES Device 静态主数据 CRUD。ECS 已能按 Endpoint 返回整批设备、运行状态、`supported_commands` 和 `supported_events`，系统管理员仍需逐项手工录入，且无法在设备管理页快速区分本次 ECS 返回中的新增、信息不一致和已接管设备。

第一版在现有设备管理页增加“从 ECS 发现”抽屉，直接复用 WES 已有的 MANUAL_DEBUG preflight 与 Device 查询/创建 API。它只进行一次按需、前端侧的当前快照比对，不新增后端 API，不建立 ECS 服务器实体，也不声称提供可靠的双向同步或原子对账。

## Decisions

1. 入口仅对系统管理员开放，即 `is_superuser=true`；普通内置“管理员”不显示入口。
2. 后端继续以 `require_superuser` 防守 `POST /api/v1/device/commands/debug/preflight`，前端隐藏不能替代后端鉴权。
3. 首版直接复用 preflight，不新增 `/api/v1/device/discovery`。
4. 每次打开后由系统管理员输入一个 ECS Endpoint 并显式刷新；不自动轮询、不保存 ECS Endpoint 列表。
5. “有变化”只表示本次 ECS 快照与当前 active WES Device 的静态身份比对结果；不表示相对历史快照发生变化。
6. 需处理项在前，未接管项其次，已接管且一致的设备最后并视觉降权。
7. `supported_commands`、`supported_events` 在抽屉设备详情中只读展示，不写入 Device 主数据。
8. 接管单台设备时复用现有 Device 创建表单，只预填设备编码、非空设备名称和 canonical Endpoint。

## NOT in Scope

- 普通内置“管理员”或其他权限角色访问：现有 preflight 是 superuser-only，首版不调整后端权限。
- 新建 ECS 服务器/Endpoint 注册资源：Endpoint 仍由用户按次输入，多个 Device 可共享同一 Endpoint。
- 后台轮询、定时同步、自动创建、批量接管或 ECS 主动推送同步：避免无确认地修改 WES 静态主数据。
- 回收站精确识别与恢复快捷入口：现有 active Device 响应不暴露删除状态，trash API 也不支持按编码过滤；创建时若撞到回收站身份，由现有 API 返回冲突。
- 原子 ECS/WES 对账：preflight 与 Device query 是两个请求，结果只能称为“本次比对”。
- 能力历史、能力变更检测或能力落库：`supported_commands/events` 只代表本次 preflight。
- 自动更新名称、Endpoint、作业线、拓扑或启停状态：不根据 ECS 响应覆盖 WES 配置。
- 用 preflight 的 `admissible/rejection_code` 决定是否接管：它们属于 MANUAL_DEBUG 命令准入，不是 Device 主数据准入。
- 新页面、新路由、新权限和后端合同变更：首版保持在现有设备管理页与冻结合同内。

浏览器始终只访问 WES。preflight 由 WES 访问 ECS，前端不得请求 `http://10.24.209.26:8080` 或其他 ECS origin。

## Current-Snapshot Reconciliation

### WES snapshot query

preflight 成功后使用其返回的 canonical `endpoint_base_url` 和 ECS `device_code` 集合查询 active Device：

```text
device_code IN <本次 ECS codes>
OR endpoint_base_url = <canonical endpoint>
```

- 使用现有 query API 的 `or` FilterGroup，不读取回收站。
- `limit=100`，按 `offset` 分页直到取得 `total`，禁止只比较第一页。
- 查询完成前不替换上一次成功结果。
- ECS codes 为空时不得发送空 `IN`；当前后端合同会拒绝空设备列表，但前端纯函数仍覆盖空输入。
- Device query 只读取本轮比对需要的 active 记录，不读取全量 Device 库，也不对每台 ECS 设备发起单独请求。

### Statuses

| Rank | Status                   | Condition                                                  | First-version action       |
| ---- | ------------------------ | ---------------------------------------------------------- | -------------------------- |
| 0    | `ENDPOINT_CONFLICT`      | 同编码 active WES Device 的 Endpoint 为空或不同            | 只读说明，不自动重绑       |
| 0    | `INFORMATION_DIFFERS`    | 同编码、同 Endpoint，但 ECS 非空名称与 WES 名称不一致      | 只读展示差异，不自动更新   |
| 0    | `MANAGED_NOT_DISCOVERED` | active WES Device 属于本 Endpoint，但本次 ECS 未返回同编码 | 只读提示，不自动停用或删除 |
| 1    | `DISCOVERED_UNMANAGED`   | ECS 返回同编码，但 active WES Device 不存在                | 允许显式接管               |
| 2    | `MANAGED`                | 同编码、同 Endpoint，且名称一致或 ECS 名称为 null          | 降权只读展示               |

规则：

- 只按完全一致的 `device_code` 关联，不按名称猜测、不推断重命名。
- Endpoint 使用 preflight 返回值与 WES 已保存值精确比较；Device 写入路径已经执行 canonical 校验。
- 名称只在 ECS `device_name !== null` 时比较，使用精确字符串相等，不 trim、不忽略大小写、不做 Unicode 归一化。
- ECS 名称为 null 表示未声明，不形成差异。
- 运行态 `is_online/mode/status/current_command_code` 展示但不参与状态分类或排序，避免实时状态导致行跳动。
- 排序键固定为 `(rank, device_code)`；同一编码最多生成一个 ECS 主项，WES-only 项来自本 Endpoint 查询结果。
- `DISCOVERED_UNMANAGED` 只是“active WES 中未找到”。它不保证回收站中没有同编码记录，UI 必须使用这一准确措辞。

## UI Composition

### Page integration

- `DeviceListPage.vue` 继续作为页面 owner，持有抽屉开关与抽屉 ref。
- `createDevicePageConfig(openDiscovery)` 增加 toolbar action：
  - label：`从 ECS 发现`
  - permission：`SUPERUSER_PERMISSION`
  - active 视图且没有批量选择时显示；回收站视图不显示。
- `CrudPageContainer` 的既有 `extra-dialogs` slot 增加两个最小 slot props：
  - `openCreate(options)`：复用 Device 创建对话框与 initial values。
  - `refresh()`：需要时刷新当前 CRUD 视图。
- 不新增第二套 Device 表单，不把 ECS 发现逻辑塞入通用 CRUD controller。

### Drawer

新增页面局部 `DeviceDiscoveryDrawer.vue`：

- 持有 Endpoint、loading、error、last-success result、filter 和 search。
- 输入 Endpoint 后必须点击刷新；打开抽屉不自动请求上一次 Endpoint。
- 一轮刷新同时包含 preflight 与 WES query；只有两侧都成功才原子替换前端展示快照。
- Endpoint 改变、抽屉关闭或新刷新开始时增加 generation；延迟返回的旧请求不得覆盖当前会话。
- 请求失败保留上一次成功结果，标记“结果已过期”，并禁用接管，直到下一次完整刷新成功。
- 默认按后端无关的本地 rank 排序；筛选和搜索只缩小结果集，不改变相对顺序。
- 桌面宽度约 720px，移动端接近全屏。

筛选组互斥：

- 需处理：`ENDPOINT_CONFLICT`、`INFORMATION_DIFFERS`、`MANAGED_NOT_DISCOVERED`
- 待接管：`DISCOVERED_UNMANAGED`
- 已接管：`MANAGED`
- 全部：不参与分组计数

文本搜索覆盖设备编码、ECS 名称和 WES 名称，大小写不敏感。分组计数之和必须等于总结果数。

### Device details and capabilities

- 行摘要显示编码、名称、分类、在线状态与当前状态。
- 点击行或“查看详情”在抽屉内展开详情，不打开新的页面。
- `supported_commands`、`supported_events` 在详情区显示完整只读标签。
- `null` 显示“未声明”；空数组显示“无”；非空数组逐项显示并允许换行。
- `MANAGED_NOT_DISCOVERED` 没有本次 ECS 快照，显示“本次 ECS 未返回设备，无能力快照”。
- `MANAGED` 行视觉降权，能力默认折叠；其他行默认展示状态原因，详情按需展开。

### Explicit onboarding

只有非 stale 的 `DISCOVERED_UNMANAGED` 行显示“接管”操作：

```ts
openCreate({
  initialValues: {
    device_code,
    ...(device_name !== null ? { device_name } : {}),
    endpoint_base_url
  }
})
```

不预填 `device_role`、作业线、上游设备、能力、运行状态或 MANUAL_DEBUG 准入结果。系统管理员补齐现有 Device 表单必填字段后提交。

创建成功后，现有 CRUD 流程先关闭表单并刷新主列表，再触发抽屉重新比对。若重新比对失败，Device 创建仍保持成功，抽屉显示旧结果并禁用再次接管；不回滚、不重复创建。

## Failure Modes

| Failure                                        | Handling                                | Test                             | User-visible result               |
| ---------------------------------------------- | --------------------------------------- | -------------------------------- | --------------------------------- |
| Endpoint 非法、ECS 不可达、非 200 或响应不可信 | 沿用 preflight 的 422/503；不提交半结果 | component error tests            | 显示可重试错误；旧结果标记 stale  |
| Device query 任一分页失败                      | 丢弃本轮全部新数据                      | query pagination error test      | 显示 WES 比对失败；旧结果不可操作 |
| 用户快速改 Endpoint 或连续刷新                 | generation guard 忽略旧响应             | delayed-response test            | 只显示最后一次请求结果            |
| 用户关闭后旧请求返回                           | session generation 失效                 | close/reopen test                | 抽屉保持初始状态                  |
| preflight 与 Device query 之间数据变化         | 标注“本次比对”；create API 最终裁决     | create-conflict integration test | 冲突提示后可重新刷新              |
| 同编码存在于回收站                             | 首版无法预识别；create 返回既有冲突     | create-conflict test             | 提示检查回收站，不声称“从未接管”  |
| 创建成功后重新比对失败                         | 不回滚创建；保留 stale 结果并禁用接管   | post-create refresh test         | 明确显示“创建成功，刷新失败”      |
| ECS 返回大量设备、WES 命中超过 100             | WES query 分页；无逐设备 N+1            | 101+ records test                | 完整稳定结果                      |
| 非系统管理员直接调用 API                       | 后端 `require_superuser` 返回 403       | 复用现有后端测试                 | 无入口；直接请求仍被拒绝          |

没有“无测试 + 无处理 + 静默失败”的已知路径。

## Performance Review Baseline

- 每次显式刷新固定为一次 preflight 加一组分页 Device query；不存在按设备 N+1。
- WES 查询只覆盖“本次 ECS codes 或本 Endpoint 已有 Device”，不扫描全库。
- 客户端 Map 比对和排序复杂度为 `O(E + W + R log R)`，其中 E 为 ECS 设备数，W 为 WES 命中数，R 为结果数。
- 不增加缓存：数据是现场即时事实，错误缓存比请求成本更危险。
- 不自动轮询：避免 ECS 和数据库持续负载，也避免运行态变化造成 UI 抖动。

## Engineering Review Results

### Architecture Review

1. `[P1] (confidence: 10/10)` Existing preflight uses `require_superuser`, while WES separately defines a non-superuser built-in “管理员”. The user selected system-administrator-only access, so the plan preserves the backend boundary and uses `SUPERUSER_PERMISSION` in the UI. Resolved.

No other architecture issues remain within the accepted frontend-only scope. The two-request non-atomic boundary, trash limitation and upgrade triggers are explicit rather than hidden。

### Code Quality Review

No issues found. The plan reuses generated APIs, the existing CRUD form and the existing stale-response pattern; it does not reuse the command-specific composable or add a second form。

### Test Review

The coverage map contains every planned branch, interaction and visible failure state. All identified paths now have a concrete unit, component or E2E requirement; zero uncovered gaps remain in the plan。

### Performance Review

No issues found. The plan uses one preflight plus a paginated, targeted WES query; it avoids full-table reads, automatic polling and per-device N+1 requests。

### Retrospective

Earlier CRUD orchestration refactors touched `CrudPageContainer`, so the generic slot-prop addition requires a regression test for existing slot consumers. No prior device-discovery implementation or reverted review cycle exists on this branch。

## Upgrade Triggers

满足任一条件时，应停止扩展此前端 shortcut，改为 Device 资源下的后端只读 reconciliation action，并复用现有 Adapter/validator/query service：

1. 普通内置“管理员”也需要访问，不能继续借用 superuser-only MANUAL_DEBUG API。
2. 必须可靠区分回收站身份、active/trash 冲突或提供恢复动作。
3. 必须提供单次一致、可审计的 ECS/WES 原子对账结果。
4. 必须保存能力历史或判断“相对上次发生变化”。
5. ECS 设备规模或 Filter payload 超过现有 query API 的安全边界。
6. MANUAL_DEBUG preflight 的响应或安全语义未来不再适合作为只读发现来源。
