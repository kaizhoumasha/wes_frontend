## Problem Statement

现场在“设备联调”页下发 `MANUAL_DEBUG` 后，只能查看当前命令的轮询结果和实时 Evidence，不能按一次联调运行查询历史，也不能把该次联调在 WES 内产生的上下游数据整体清除。命令进入 `RECONCILING` 等非终态后会继续占用设备槽位，操作人员为修改参数重新验证，只能人工定位并删除多张表的数据。

这里要解决的不是“删除一条 DeviceCommand”，而是建立一个可证明归属的“联调试运行”，使 WES 能查询并原子清理这次试运行拥有的完整本地数据链。ECS 的数据、队列和状态不由 WES 清理，继续由供应商处理。

## What Makes This Cool

操作人员不再记表名、写 SQL 或猜测关联关系。选中一个联调 Epoch 后，页面先展示服务端计算的 WES 归属清单，再用一次原子操作清空该 Epoch 的完整本地链路。即使存在 `ACTIVE`、`ACKNOWLEDGED` 或 `RECONCILING` 命令，WES 也能按用户确认的边界直接释放本地阻塞，同时用持久 tombstone 防止迟到回调把已清理链路重新写回。

## Constraints

- 只清理 WES 数据；不得调用 ECS 的清理、取消或修改接口，也不得声称 ECS 已停止执行。
- 清理范围是一个明确的联调 Epoch，不支持按设备、时间段、`trace_id` 或模糊可达关系批量删除。
- 联调 Epoch 只能属于专用测试 WorkLine；正式 WorkLine 必须在服务端拒绝查询清理和联调命令接入。
- 清理允许作用于非终态 WES 数据，不等待 ECS 或物理侧确认。这是用户明确接受的风险边界。
- 只有系统超级管理员可查询完整清单、创建联调运行和执行清理；前端隐藏不能替代后端鉴权。
- 旧的无 Epoch 归属数据允许只读查询，不自动补归属、不允许整链清理。
- 不新增动态删除注册表、兼容层或通用“任意业务链删除平台”；首版使用静态、可测试的 ownership manifest。
- WorkLine、Device、Rack、Bin 等静态主数据不属于一次联调 Epoch，禁止删除。
- 清理不可撤销；唯一保留的是独立于 Epoch 的最小审计与迟到消息 tombstone。

## Premises

1. 一次需要整体重跑的现场调试，业务根应是现有 `LineRunEpoch`，而不是单个 `DeviceCommand` 或仅用于检索的 `trace_id`。
2. “关联可达”不等于“归该次联调独占”。只有显式 `line_run_epoch_id` 或从独占父记录出发的静态子关系，才能进入删除清单。
3. 专用测试 WorkLine 是允许直接清理非终态链路的隔离边界；同一规则不得扩展到生产 WorkLine。
4. WES 释放本地设备槽位不代表物理动作终止。页面和审计必须持续显示“ECS 可能仍有在途任务”。
5. Preview 是删除合同，不是装饰性统计。实际 Reset 必须锁定后重新计算同一份 manifest；任何漂移都整单拒绝。

## Decisions

1. **只处理 WES。** ECS 历史、队列、状态与取消由供应商负责，WES Reset 不读写 ECS。
2. **清理完整上下游链。** 命令、Evidence、Session、Timeline、执行、运输、位置/资源运行投影、安全事件等，只要可证明由该 Epoch 独占拥有，都进入同一事务。
3. **以 `LineRunEpoch` 为唯一根。** 不新建 `OpsDebugRun`，也不以 `trace_id` 替代所有权。
4. **只允许专用测试 WorkLine。** WorkLine 增加服务端可校验、默认安全的用途字段；生产用途永远不能调用 Debug Reset。
5. **允许直接清理非终态链路。** 不要求“供应商已清 ECS”或“物理目标已到达”的声明；确认框只要求操作员理解 WES-only 风险。
6. **旧数据只读。** `line_run_epoch_id IS NULL` 的历史 `MANUAL_DEBUG` 可以展示为 `LEGACY_UNOWNED`，但清理按钮禁用。
7. **删除后保留最小审计和 tombstone。** 它们不是业务运行数据，不参与下一次调试，也不能被本功能删除。

## Approaches Considered

- **单命令清理：已否决。** 不能覆盖反复调试形成的 Session、执行、Evidence、Transport 和投影链。
- **新增 `OpsDebugRun`：已否决。** 用户选择复用现有 WorkLine/LineRunEpoch 生命周期，避免第二套运行根。
- **`trace_id` 作为删除根：已否决。** 当前 `MANUAL_DEBUG` 不写 `trace_id`，且 trace 只是追踪字段，不能证明独占所有权。
- **现有 `LineRunEpoch` 作为根：采用。** 复用冻结绑定和 Epoch 生命周期，但必须显式扩展现有 MANUAL_DEBUG 不带 Epoch 的约束。

## Recommended Approach

### 1. 建立不可伪造的联调用途边界

给 WorkLine 增加枚举字段：

```text
purpose = PRODUCTION | ONSITE_DEBUG
default = PRODUCTION
```

- 既有 WorkLine 迁移为 `PRODUCTION`。
- `purpose` 创建后不可随意改写；存在任何 Epoch 后禁止变更，避免把生产历史重新标成可删除数据。
- 现有 WorkLine START 继续创建 `LineRunEpoch`，但设备联调页只列出 `purpose=ONSITE_DEBUG` 的 WorkLine。
- WorkLine create/update 沿用现有管理权限，但创建 `ONSITE_DEBUG`、把无 Epoch 的 WorkLine 从 `PRODUCTION` 改为 `ONSITE_DEBUG`、以及 START 一个 `ONSITE_DEBUG` WorkLine 都额外要求 `require_superuser` 并写审计。`ONSITE_DEBUG` 不允许改回 `PRODUCTION`；误建时只能在尚无 Epoch 且没有运行引用时软删除。
- 一条 WorkLine 仍只允许一个 `ACTIVE` Epoch，复用现有唯一约束；不允许调试 Epoch 与同线生产 Epoch 并行。
- WorkLine 本身及冻结配置来源不随 Reset 删除。

### 2. 让 MANUAL_DEBUG 真正归属 Epoch

当前 `DeviceCommand` 数据库约束要求 `MANUAL_DEBUG.line_run_epoch_id IS NULL`，创建 API 也硬编码 `trace_id=None`。新合同改为：

- `POST /api/v1/device/commands/debug/preflight` 接收 `line_run_epoch_id`，服务端只加载该 ONSITE_DEBUG Epoch 的冻结设备绑定，并按绑定 Endpoint 获取状态。
- `POST /api/v1/device/commands/debug` 必须提交 `line_run_epoch_id` 和 `device_code`。
- 服务端从 `LineRunEpochDeviceBinding` 取得 Endpoint、合同版本和超时；客户端不再为已绑定运行任意指定 Endpoint 或 timeout。
- 新 `MANUAL_DEBUG` 写入 `line_run_epoch_id`、`device_binding_id`，保持 `material_execution_id=NULL`，并继续保留 `execution_reason`、`created_by` 和唯一 `client_request_id`。
- 数据库约束改为允许且要求上述 Debug Epoch 上下文；正式业务命令约束不变。
- 调度和回调处理必须把 Epoch 身份继续传播到 `InboundEvidence`、执行、Transport authority 和 Session。

该改动是有意的合同收紧，不保留“新页面仍可创建无 Epoch MANUAL_DEBUG”的旁路。

### 3. 补齐跨模块 ownership

首版迁移必须新增：

- `LineRunEpoch.reset_generation`：默认 0；所有 Epoch-owned writer 冻结该值，Reset 持锁后递增以废止旧 writer。
- `WorklineSession.line_run_epoch_id`：既有数据可空；新建 ONSITE_DEBUG Session 时必填且与 `workline_id` 一致。
- `DeviceStatusObservation.line_run_epoch_id`、`WorklineSafetyIncident.line_run_epoch_id`、`RuntimeLocationEvent.line_run_epoch_id`、`CallbackLog.line_run_epoch_id`、`WorklineRuntimeStatusProjection.line_run_epoch_id/reset_generation`：既有数据可空；Debug Epoch 新写入必须非空。
- `ObjectTransitionEvent.workline_session_id` 与 `BinContentSnapshot.source_session_id` 改为真实 FK；Debug 写入不得只有 trace/code 软引用。
- Transport 联调任务使用现有 `authority_line_run_epoch_id`，不再仅依赖固定 debug caller 常量。
- 新增独立的 `DebugEpochResetIdempotency`、`DebugEpochResetAudit`、`DebugEpochResetTombstone` 持久表；三者不使用目标 Epoch FK，避免 Epoch 删除后丢失重试结果、审计和迟到消息围栏。

归属规则只有两种：

1. **直接所有权：** 行上 `line_run_epoch_id = target_epoch.id`。
2. **独占子所有权：** 行通过静态定义的外键或稳定唯一键指向已归属父记录，例如 Timeline → Session、EvidenceConflict → Evidence、TransportMember → TransportTask。

以下情况一律不加入删除清单：

- 只因 `trace_id`、设备编码、WorkLine ID 或时间接近而命中；
- 指向静态主数据；
- 同时被其他 Epoch 或无归属记录引用；
- ownership manifest 不认识的新表或新关系。

遇到最后三类时 Preview 返回 `OWNERSHIP_INCOMPLETE` 并禁止清理，而不是尽量删除。

每个条目在代码中是固定 `ManifestRule(table, owner_predicate, operation, order, blocker_query)`，Preview 和 Reset 共用同一个 rule 集。规范性清单同时维护两份静态 inventory：数据库 FK 引用与 code/trace/operation 等 soft-reference writer；CI 比较 SQLAlchemy metadata 和显式 soft-reference 列表，出现未分类的新引用或写入路径时测试失败。

Preview 对每条 rule 返回 `delete_count`、`update_count`、`cycle_break_count` 和 `blocker_count`，不返回可能包含 payload 的行级数据。页面承诺的是“完整分类摘要”，不是原始记录导出。

`MaterialUnit` 等共享主记录不直接删除；如果仅有 `current_session_id` 指向目标 Session，则先在同一事务内清空该运行引用。这里“共享”精确定义为：同一行存在目标 manifest 外的非空 FK/稳定 owner，或目标测试资源存在非目标 active Session/Execution/Transport 引用；“不可恢复前态”精确定义为需要改写静态主数据或生产 WorkLine 当前投影才能完成 Reset。两者都返回带 `rule_id`、table、count 的 blocker，不返回业务 payload。专用测试 WorkLine 应使用隔离测试资源，避免这种阻塞。

实现不得依赖数据库级无边界 cascade。每个 repository 返回实际删除/更新数量，Reset 结果必须与锁内 manifest 一致。

### 5. Preview、锁与原子 Reset

流程：

```text
GET reset-preview
  -> require_superuser
  -> load Epoch + WorkLine purpose
  -> build static ownership manifest
  -> reject ambiguous/shared ownership
  -> enforce capacity ceiling
  -> return per-rule counts + signed preview_token + warnings

POST reset
  -> require_superuser
  -> try-acquire existing epoch lifecycle advisory lock
  -> lock Epoch and owned roots in fixed order
  -> rebuild the manifest
  -> preview_token mismatch/expired => 409 PREVIEW_STALE, delete nothing
  -> write reset audit/tombstone
  -> break only manifest-internal cycles
  -> delete children, roots, bindings, Epoch
  -> verify every actual count
  -> commit once
```

Reset body：

```json
{
  "client_request_id": "uuid",
  "epoch_code": "DBG-...",
  "preview_token": "<returned-by-reset-preview>",
  "acknowledgement": "WES_ONLY_ECS_MAY_STILL_BE_ACTIVE"
}
```

`acknowledgement` 只证明用户看到了风险，不证明 ECS 已清理或设备安全。服务端不得据此生成物理完成事实。

锁协议固定为：`epoch_lifecycle_lock_identity(epoch.id)` advisory transaction lock → Epoch row → manifest rules 由小到大。Reset 最多等待锁 2 秒；如果同一 idempotency record 已是 `IN_PROGRESS`，返回 `RESET_IN_PROGRESS`，否则返回 `EPOCH_BUSY`，并要求重新 Preview。普通 writer 最多等待同一 Epoch 锁 5 秒，超时后按其既有可靠重试/RECONCILING 语义处理，不能绕过锁。所有创建/更新 Epoch-owned Command、Session、Evidence、Execution、Transport 与 resource runtime row 的 writer，都必须在其数据库事务内先获取同一 Epoch lock，并用 `WHERE epoch_id=? AND reset_generation=?` 或等价 FK 存在条件写入；检查与写入不得跨事务。

Preview 将当前 generation 记为不可变 `target_generation`。Reset 锁定 Epoch 后验证它仍等于 token 中的 `target_generation`，所有 manifest rule、count 和 owner predicate 始终使用该旧值；随后把持久 Epoch generation 递增以废止旧 writer，但绝不把 manifest 的选择条件切到新值。这样 rule 10 仍能更新带旧 generation 的 projection，而等待锁的 writer 在获得锁后因 generation 条件不匹配而 no-op。最终 Epoch 在同一事务删除。

Preview token 是服务端签名的短期 opaque token，绑定 `epoch_id`、`epoch reset_generation`、规范化 manifest version/digest、当前用户 subject 和 10 分钟 expiry。manifest canonical form 是按 rule order 排序的 `{rule_id, delete_ids_digest, delete_count, update_ids_digest, update_count, blocker_count}`。`PREVIEW_STALE` 不返回可直接提交的新 token，前端必须重新 GET Preview 并重新确认。

首版容量上限固定为 manifest 总 DELETE 50,000 行、UPDATE 5,000 行；Preview 超限返回 `RESET_TOO_LARGE` blocker 和分类计数，禁止同步 Reset。该上限只面向隔离测试 Epoch，不提供分批删除旁路。

Reset 使用独立 idempotency record，key 唯一绑定 `subject + epoch_code + intent hash`，其中 intent hash 只包含 epoch_code 与 acknowledgement，不包含有有效期的 preview token。状态为 `IN_PROGRESS | SUCCEEDED | FAILED_RETRYABLE | FAILED_FINAL`。

请求首先按 key 查询/锁定 idempotency record，再查询 Epoch：不存在时用短事务创建 `IN_PROGRESS`、`lease_until=now+5min`；同 key 不同 subject/Epoch/intent 返回 `IDEMPOTENCY_CONFLICT`；有效 lease 的 `IN_PROGRESS` 返回 `RESET_IN_PROGRESS`；过期 lease 可由同一 intent 以 CAS 递增 attempt 并携带新 Preview token 接管。主 Reset 事务同时锁住 idempotency record 和 Epoch，并在同一次 commit 中完成删除、成功 audit、`SUCCEEDED` 状态和完整响应快照，所以进程崩溃后不会出现“Epoch 已删但结果未存”。主事务最长 120 秒，超时整体回滚；回滚后独立事务写 `FAILED_RETRYABLE`。`SUCCEEDED` 在 Epoch 已不存在时仍直接返回存储结果；合同/ownership 错误记为 `FAILED_FINAL`。

非成功路径的 idempotency 转换固定如下；状态更新与对应错误响应前的最后一次数据库写在同一短事务完成：

| Outcome                                                                   | Idempotency action                                             | Retry rule                                    |
| ------------------------------------------------------------------------- | -------------------------------------------------------------- | --------------------------------------------- |
| `PREVIEW_STALE`、`EPOCH_BUSY`、数据库超时/瞬时异常                        | `FAILED_RETRYABLE`，清空 lease，保存 error code                | 同 key/intent 可携带新 Preview token 立即重试 |
| `RESET_TOO_LARGE`、`OWNERSHIP_INCOMPLETE`、`PROVIDER_IDENTITY_NOT_STABLE` | `FAILED_FINAL`，清空 lease                                     | 条件修复后使用新 key 和新 Preview             |
| `PRODUCTION_WORKLINE_FORBIDDEN`、非法 acknowledgement                     | `FAILED_FINAL` 或在服务前 validation 拒绝，不留下 active lease | 修正请求后使用新 key                          |
| `IDEMPOTENCY_CONFLICT`                                                    | 不修改已存在 record                                            | 使用与原 intent 一致的请求或新 key            |
| `RESET_IN_PROGRESS`                                                       | 保持原 `IN_PROGRESS` lease                                     | lease 内等待；过期后按 CAS 接管               |
| Success                                                                   | 主 Reset 事务内写 `SUCCEEDED` 和 response snapshot             | 同 key 永久返回原结果                         |

### 6. Active/RECONCILING 直接清理与迟到写入围栏

按已选方案，Reset 不检查命令是否终态，也不等待 ECS：

- Epoch lifecycle lock 与 reset generation 阻止新的 WES 命令、Session、执行和 Transport 在 manifest 建立后接入。
- 已经发起外部 HTTP、但尚未写回的 worker 必须在同一写事务中获取 Epoch lock并做 generation 条件写入；目标已 reset 时 affected rows 为 0，随后查 tombstone 并 no-op，不得重建行。
- Reset 为每个退休身份保存可索引 tombstone：`identity_type`、`provider_scope`、规范化 identity hash、`reset_audit_id`，并以三元组唯一约束去重；聚合 digest 只用于清单完整性校验，不能替代查询索引。tombstone 不自动过期。只有能保证稳定 identity 永不复用的 provider 才允许 Reset；否则 Preview 返回 `PROVIDER_IDENTITY_NOT_STABLE` blocker，直到合同增加可区分 generation。
- Device/Transport callback ingress 必须先用规范化 provider identity 查询 tombstone，再决定是否创建完整 CallbackLog/Evidence。命中退休 identity 时只原子增加 reset audit 的迟到计数并返回 `IGNORED_DEBUG_EPOCH_RESET`，不保存原始 callback payload。
- 审计只保存识别、计数、digest、操作者和时间，不复制完整业务 payload。
- 不带可退休稳定身份的后续 unsolicited ECS EVENT 无法被 WES 证明属于旧 Epoch；它按当时有效的入口规则处理。UI 必须说明直接清理不能阻止 ECS 继续发送新事实。

### 7. API 合同

新增 WorkLine-owned 运维接口，全部 `require_superuser`：

| Method | Path                                                       | Purpose                                                                                              |
| ------ | ---------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| GET    | `/api/v1/workline/debug-epochs`                            | `workline_id`、`status`、大小写敏感 `epoch_code_prefix`、精确 `operator_id` 与 cursor 查询联调 Epoch |
| GET    | `/api/v1/workline/debug-epochs/{epoch_code}`               | 返回 Epoch 摘要、异常状态与分类计数                                                                  |
| GET    | `/api/v1/workline/debug-epochs/{epoch_code}/reset-preview` | 返回精确 manifest、警告与 preview token                                                              |
| POST   | `/api/v1/workline/debug-epochs/{epoch_code}/reset`         | 原子删除该 Epoch 的 WES-owned 链路                                                                   |
| GET    | `/api/v1/workline/debug-epoch-reset-audits`                | 按 Epoch code、client_request_id、操作者与时间游标查询 Reset 审计                                    |
| GET    | `/api/v1/workline/debug-epoch-reset-audits/{audit_id}`     | 返回分类计数、风险边界、结果与迟到消息计数；不返回原始 payload                                       |
| GET    | `/api/v1/device/commands/debug/legacy`                     | 分页只读查询无 Epoch 的旧 MANUAL_DEBUG；不可清理                                                     |

既有 WorkLine START 用于“新建联调运行”，不复制第二个 Epoch 创建 API。START 必须校验 WorkLine purpose 并保持“一线一个 ACTIVE Epoch”。

Preview 的规范响应为：`epoch` 快照、`manifest_version`、按 rule order 排列的 `items[{rule_id, operation, delete_count, update_count, cycle_break_count}]`、`blockers[{rule_id, code, count}]`、总计、warnings、`preview_token` 和 `expires_at`。不返回行级 ID 或 payload。Reset success 返回相同计数字段的实际值、`audit_id` 和 `client_request_id`。

主要错误语义：

- `403`：非超级管理员。
- `404`：Epoch 不存在，或 idempotency key 无对应的已完成 Reset。
- `409 PRODUCTION_WORKLINE_FORBIDDEN`：目标不是 ONSITE_DEBUG WorkLine。
- `409 PREVIEW_STALE`：锁内 manifest 与预览不同；响应携带新的 summary，前端要求重新确认。
- `409 OWNERSHIP_INCOMPLETE`：发现共享、歧义或未登记引用；不删除任何数据。
- `409 RESET_IN_PROGRESS`：同一 idempotency request 的有效 lease 尚未结束。
- `409 EPOCH_BUSY`：普通 Epoch writer 占锁超过 Reset 的 2 秒等待窗口。
- `409 IDEMPOTENCY_CONFLICT`：同 key 对应不同 subject/Epoch/intent；preview token 不参与冲突判定。
- `409 RESET_TOO_LARGE`：manifest 超过同步 Reset 上限。
- `422 ACKNOWLEDGEMENT_INVALID`：确认枚举或输入的 epoch_code 不匹配。

游标均为服务端 opaque token，只提供向后翻页：Epoch 固定按 `(started_at DESC, id DESC)`，legacy command 按 `(created_at DESC, id DESC)`，Reset audit 按 `(requested_at DESC, audit_id DESC)`；筛选条件摘要绑定在 cursor 中，条件改变必须从第一页重新查询。

### 8. 前端交互

在现有 `/ops/device-diagnostics` 页面增加两个 Tab：

- `实时 Evidence`：保留现有行为。
- `联调运行历史`：按 ONSITE_DEBUG WorkLine 查询 Epoch，支持状态、Epoch code、操作人和游标分页。

历史列表：

- 行展示 Epoch code、测试 WorkLine、ACTIVE/CLOSED、开始时间、操作人和分类计数。
- 选中后加载详情和 manifest summary，不在浏览器自行拼接删除范围。
- `LEGACY_UNOWNED` 使用历史 Tab 内独立折叠区块和独立 cursor，不混入 Epoch 列表、筛选计数或分页；清理按钮禁用并说明原因。

清理流程：

1. 点击“预检并整链清理”获取服务端 preview。
2. 红色确认框明确显示“只清 WES；不等待、不清理 ECS；ECS 可能仍有在途任务”。
3. 展示分组计数和 blocker；存在 blocker 时不显示确认按钮。
4. 用户输入完整 `epoch_code`，勾选“理解 WES-only 风险”，提交 preview token。
5. 成功后移除已删除 Epoch、刷新列表和实时流；显示实际删除计数及独立审计编号。
6. `PREVIEW_STALE` 时关闭确认态并展示新 preview，禁止沿用旧确认。

前端复用 Transport reset 的“preview → danger dialog → refresh”交互模式，但不把两种业务强行抽成通用删除组件。

### 9. Audit

Reset 审计独立于目标 Epoch，至少记录：

- `client_request_id`、epoch id/code、WorkLine id/code/purpose 快照；
- 操作者、请求时间、完成时间；
- preview token/manifest version、各分类实际删除数量；
- reset 前命令状态分布，包括非终态数量；
- `WES_ONLY_ECS_MAY_STILL_BE_ACTIVE` 风险确认；
- tombstone identities 的 digest 和迟到消息计数；具体可检索 identity 存在独立、长期保留的 tombstone 表；
- 成功或回滚结果，不保存完整命令参数和外部 payload。

成功审计、idempotency success response 与删除在同一事务提交，保证不会出现“审计成功但业务回滚”或“Epoch 已删但重试结果丢失”。删除事务失败后先完整回滚，再用独立事务写失败 attempt，明确 `deleted=false` 和错误分类；失败审计不能表示发生过部分删除。Reset 审计按既有审计策略长期归档；退休 identity tombstone 不自动删除，也不提供本 Reset API 的删除入口。

审计记录不能作为物理完成、ECS 已取消或供应商已处理的证据。

## Failure Modes

| Failure                         | Required behavior                                                            |
| ------------------------------- | ---------------------------------------------------------------------------- |
| 正式 WorkLine 被请求清理        | 服务端 409，零写入；不能依赖前端过滤                                         |
| Preview 后新增或迟到 WES 数据   | Reset 锁内重算，token 不同则 409，零删除                                     |
| manifest 发现共享/未知引用      | `OWNERSHIP_INCOMPLETE`，列出 blocker 分类，零删除                            |
| 删除中任一计数不符或数据库异常  | 整个业务事务回滚；回滚后以独立事务记录 `deleted=false` 的失败摘要            |
| Reset 响应丢失                  | 同一 `client_request_id` 返回原结果                                          |
| 已派发 worker 晚于 Reset 写回   | tombstone/fence 使写回 no-op，不重建业务行                                   |
| ECS 迟到 callback 带退休身份    | 忽略业务应用，审计计数增加，不推断物理结果                                   |
| ECS 继续发送无旧身份 EVENT      | 作为新入口事实处理；页面警告此风险，不声称已隔离 ECS                         |
| 清理后马上重发新参数            | 新 Epoch/新 command identity 正常创建；旧身份不能占用 WES 槽位               |
| 老 MANUAL_DEBUG 无 Epoch        | 可只读查询，清理被拒绝                                                       |
| manifest 超过容量上限           | `RESET_TOO_LARGE`，展示分类计数，零删除且无分批旁路                          |
| provider identity 可能复用      | `PROVIDER_IDENTITY_NOT_STABLE` blocker；未增加可区分 generation 前禁止 Reset |
| Reset 等待普通 writer 超过 2 秒 | `EPOCH_BUSY`，零删除；前端等待后重新 Preview                                 |

## NOT in Scope

- ECS/RCS/WMS 供应商系统中的删除、取消、复位或状态修改。
- 自动判定设备已停止、物理目标已到达或可安全重发。
- 正式 WorkLine、正式 Epoch 或共享生产资源的清理。
- 按 Device、WorkLine 全量、时间范围或任意 SQL 条件批量清理。
- 多 Epoch 批量 Reset、撤销/恢复、回收站或数据导出。
- 自动给旧命令、旧 Session 猜测并回填 Epoch。
- 通用动态图遍历、插件式删除注册中心或数据库无边界 cascade。
- 本设计阶段的实现、提交、发布和现场部署。

## Success Criteria

- 超级管理员能在设备联调页分页查询 ONSITE_DEBUG Epoch 及其 WES 分类计数。
- 新建 `MANUAL_DEBUG` 必须属于一个 ACTIVE ONSITE_DEBUG Epoch，并使用冻结 Device binding。
- 一个含 Session、Timeline、命令、Evidence、执行、Transport、投影和安全记录的测试 Epoch，Preview 与 Reset 的每条 rule `delete_count/update_count/cycle_break_count` 完全一致。
- 含 `RECONCILING` 命令的测试 Epoch 可直接 Reset；完成后同设备 WES unclosed-command 槽位释放。
- Reset 不产生任何 ECS 请求，不能修改 ECS 历史、队列或状态。
- 正式 WorkLine、旧无归属命令、共享资源引用和未知 ownership 都 fail closed 且零部分删除。
- Preview 漂移、数据库异常和并发 Reset 均保持原子性，无半清理。
- 迟到 command/transport callback 不会重建已清业务链；审计能解释为何被忽略。
- Reset 审计在 Epoch 删除后可按 audit id、Epoch code 或 client request id 查询，且明确 `business_authoritative=false`、`physical_completion=false`。

## What I noticed about how you think

- 你先把责任边界钉死为“只需要完整的清理 WES 内的数据即可，ECS 的数据由供应商自行处理”，避免功能悄悄跨成供应商系统编排。
- 你强调“上下游数据需要反复调试”，说明真正要恢复的是一次试运行，而不是让一条卡住的命令看起来消失。
- 你选择复用 `LineRunEpoch`，同时限定专用测试 WorkLine，倾向用现有业务根建立可验证边界，而不是再造一个平行运行模型。
- 你接受不等待 ECS 的直接清理风险，是为了现场迭代速度；设计因此必须把“释放 WES 阻塞”和“物理动作已经停止”严格分开。
